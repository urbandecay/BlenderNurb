# Solid and NURBS Boolean analysis and implementation plan

Date: 2026-11-10. Based on the working tree, including its uncommitted Solid work.
This is a code review and proposed architecture, not completed implementation or
a new runtime diagnosis of the user's scene. No Blender session was changed.

Implementation has started with the Phase 0 operation contract, native regression
fixtures, structured timing diagnostics and failure-request capture/replay. See
`BOOLEAN_DEBUG.md` for usage and current limits. Stored NURBS, UV trims, shell/body
ownership and general curved partitioning remain subsequent milestones. The
original user scene has not yet been captured and replayed, so Phase 0 remains
in progress.

Verified this milestone in the existing `build_linux` directory: all 15 native
Solid test executables pass, the two new host contract checks pass (including
failed-case capture and command-line replay), and seven existing Boolean host
tests pass (including volumes, source selection, result selection and reload).
The Blender executable and standalone replay tool have been rebuilt. These
checks do not establish general curved/NURBS support or interactive viewport
performance.

## Decision

Keep the native Solid model and Blender host adapter. Expand the model into a
general trimmed B-rep, then develop the native Boolean pipeline against it.
The user's decision is native only: all Boolean geometry calculations and
topology construction run on the app's own kernel data. The experimental OCCT
runtime, conversion bridge and backend have been removed. Existing user files
retain their native sources. The notes below describe the limits of the removed
bridge and do not propose bringing it back.

The largest missing foundation is not another list of primitive names. It is
the ability to represent, validate, display and edit arbitrary trimmed surfaces
and the curves generated by their intersections. Porting Boolean routines alone
cannot solve that gap. Studying established algorithms can inform implementation;
any adapted source retains its attribution and licensing obligations. That does
not require linking or running the OCCT kernel.

## Scope and meaning of NURBS

A solid describes a closed volume. NURBS describe curves and surfaces. A solid
may therefore contain NURBS faces alongside planes and cylinders, and should
use the same Boolean pipeline. A standalone NURBS curve has no volume. An open
NURBS sheet does not define an unambiguous inside and outside by itself.

Initial volume scope: valid, oriented, closed manifold bodies, including mixed
analytic/NURBS faces, several disconnected result bodies and cavity shells.
Surface scope: intersection, split and trim of bounded sheets, plus stitching
compatible sheets into solids. A sheet cutting a solid needs explicit split or
half-space semantics; it must not be silently treated as an ordinary solid.
Self-intersecting or otherwise invalid inputs need a diagnostic and a separate
repair workflow. No credible plan promises every possible input will succeed.

| Classification | `classify.cc`, `SOL_classify.hh` | Face/body tests are limited to supported plane/cylinder/conic-extrusion cases with line/conic trims. Unsupported geometry explicitly fails. |

| Operator | `edit_solid_boolean.cc` | Currently selects disconnected face components within one Solid edit session; mesh solvers use derived display geometry. This is not a general cross-object NURBS operator. |
| Body ownership | `components_for_faces`, `face_components` | Bodies are inferred from connected faces. An enclosed cavity boundary is a separate connected shell, not a separate material body; that distinction needs explicit representation or a certified containment index. |
| Blender hosting | `DNA_mesh_types.h::Mesh::solid_storage`, `DNA_solid_types.h`, `BKE_solid_host.hh` | Solid source lives on a normal Mesh datablock. There is no separate Solid object type required for this plan. |
| Selection/display | `solid_host.cc::display_mesh/read_edit`, `editsolid.cc::replace_display` | Sampled display elements carry `.solid_*_id` mappings back to source entities. Display samples are not editable source control points. |
| Source transforms | `geometry.cc::transform_selected`, `transform_convert_solid.cc` | Whole/isolated component transforms have preview paths. Partial curved deformation already fails without a construction rule. |
| Persistence | `storage.cc`, Mesh copy/read/write hooks in `blenkernel/intern/mesh.cc` | Source schema is version 6; additions require explicit migrations and updated validation, copy, undo and reload handling. |

The earlier conversational claim that general NURBS were already stored in
Solid was incorrect. The standalone spline evaluator does not establish that.
Blender's existing NURBS objects and this fork's Solid source also need an
explicit adapter; sharing an application does not connect their representations.

## Findings in priority order

1. **The kernel cannot represent general Boolean output.** Intersecting two
   simple curved surfaces can generate a curve outside the four stored curve
   kinds. Adding a surface kind without those intersection curves is insufficient.
2. **The native pipeline is incomplete across several stages.** General curved
   face intersection, bounded UV face arrangement, coincidence handling and
   result reconstruction are needed together. Replacing the final error with
   another special branch does not supply these stages.
3. **A closed result is not proof of the correct set operation.** Native result
   validation can check topology and storage, but does not by itself prove an
   allegedly successful Union contains both inputs. Empty intersection can be
   correct; loss of all material from a nonempty Union cannot. This deserves a
   dedicated result contract and diagnostics. These are review findings, not
   proof of where the screenshot's cylinder went.
4. **Trims are currently underspecified for general curved faces.** `Coedge`
   stores edge ID and reversal, not its curve in that face's parameter space.
   General NURBS, poles and repeated seam occurrences need durable source data.
5. **Editable Boolean results require additional operations.** A trimmed NURBS
   surface may retain its original control net while a new boundary cuts through
   it. Moving that boundary vertex is different from moving a control point.
6. **Interaction and attribute support are part of the delivery.** Missing
   ancestry, unsupported partial edits, tessellation costs and lost face
   appearance would make mathematically successful Booleans feel broken.

## Phase 0 — Establish correctness and observability

Before expanding solver scope, reproduce the disappearing-body case using
saved native source data. Capture selected body IDs, active operand, operation,
cutter options and transform matrices. Separate geometry loss from operand
selection, result publication and display problems.

Add an opt-in operation trace with stage timings: input extraction,
intersection, partition/classification, reconstruction, validation, tessellation
and Blender publication. Retain bounded structured records with the native
algorithm path and warnings. Capture native operands/results for failed cases.
Viewport draw intervals require a separate draw measurement; transform callback
time is not FPS. Current profiling is environment-gated stderr output.

Acceptance cases must include a three-cylinder chain, a previously Booleaned
body joined to a fresh cylinder, disjoint bodies and fully contained bodies.
Use deterministic replay fixtures; pictures alone cannot establish topology.
Check volume and material membership where expected values are known, boundary
validity, absence of unintended faces, and continued editing/reload. Result body
count alone is not an invariant: a correct union can contain multiple bodies.

Output: deterministic regression fixtures and stage diagnostics. Record whether
the native path currently rejects each fixture or returns an incorrect result.
Unsupported cases become acceptance targets for later phases; they must preserve
the source rather than force a premature geometry workaround.

## Phase 1 — Expand the native B-rep and file format

Preserve stable source IDs and analytic types. Add stored rational B-spline
curve and surface payloads using the existing math as a starting point:
degree, knots, poles, weights, domain, periodicity/closure information. Keep
analytic circles and ellipses analytic when possible. Use payload tables or
tagged data with explicit ownership instead of growing an ambiguous bag of fields.

Add 2D parameter-space trimming curves per edge use, parameter correspondence
with the 3D edge, seam occurrences, and degenerate pole boundaries. Two faces
may share one 3D edge but require different 2D curves. Face parameter-space
coordinates are not the same thing as an artist's texture UV map.

Add body/shell membership, orientations and nesting for cavities. A derived
index is acceptable if it is stable and validated; an explicit Shell/Body layer
is recommended because selection and operation ownership need this information.

Define model-unit tolerances and per-entity measured errors, replacing unrelated
hardcoded thresholds gradually. Preserve analytic supports where possible;
general surface intersection curves often require bounded approximation. Record
that error and enforce a budget rather than calling all spline results exact.

Extend result data with source ancestry, attribute transfer and diagnostics.
Persist surface/material associations and texture parameterization where needed.
Version the source schema; retain readers for old data, use bounded array reads,
and verify old files, copy/duplicate, undo/redo and save/reload.

Acceptance: a trimmed NURBS face and a mixed analytic/NURBS solid survive storage,
copy, selection and reload, including holes, seams and a nested cavity.

## Phase 2 — Geometry services and viewport support

Expose consistent evaluation, derivatives, domains, normals, bounded boxes and
point-to-surface projection/inversion for all supported surface types. Extend
the standalone spline math with the operations required by projection and
intersection (including higher derivatives where the selected algorithms need them).
Handle finite domains, knot multiplicities, periodic knots and singularities.

Upgrade validation from compact construction-layout assumptions to trimmed
surface checks: loops close, edges lie on both incident faces within tolerance,
orientations and containment agree, and boundary crossings are understood.

Implement adaptive tessellation of UV-trimmed faces. Share sampled boundary
edges between neighboring faces, retain source IDs, and avoid cracks at seams
and poles. Geometry calculations retain double precision; Blender display
precision and GPU picking need their own error expectations.

Add adapters for Blender NURBS curves/surfaces using their real control points,
weights and knot conventions. Verify evaluated positions/derivatives against
the original Blender surface. Exporting a display mesh is not a NURBS adapter.
Represent open sheets explicitly; stitching is a separate operation.

Acceptance: view, select and transform trimmed NURBS data without changing its
source when display density changes. Native Blender NURBS conversion preserves
the measured geometry across periodic and nonperiodic examples.

## Phase 3 — Native operation contract and source history

Introduce a result containing status (success, intentional empty, unsupported,
invalid input, numerical uncertainty, failed), model, ancestry, warnings and
timings. A successful result must satisfy the operation's checks before publish.
Retain the existing immutable snapshot/revision transaction pattern.

Produce ancestry directly during native splitting and reconstruction: retained,
modified, generated and deleted entities. Use it to remap active elements,
selection, material assignments and texture mappings. Operand extraction must
operate on body/shell ownership rather than blindly treating every disconnected
face component as a separate solid.

Make every supported operation return this contract. Unsupported geometry stays
explicit while native coverage grows; no external solver fallback is used.
Reference expectations come from analytic examples, set-operation identities,
independently checked fixtures and integration checks.

Acceptance: native source encode/decode preserves richer geometry and topology;
repeated Booleans preserve membership, attributes and editability. Empty success
is distinguished from an unsuccessful reconstruction or discarded geometry.

## Phase 4 — Complete the native Boolean pipeline

1. Build conservative bounds and candidate face pairs; avoid global all-pairs
   work where bounds exclude interactions.
2. Maintain one shared intersection graph across operands. Reconcile vertices,
   edge events, face events and coincident pieces before constructing results.
3. Preserve fast analytic intersection cases and add a general parametric
   surface intersector: bounded patch subdivision, seed discovery, corrected
   curve tracing, UV curves on both supports and measured residuals. Bound all
   searches and classify uncertain results explicitly. Closed intersection
   loops, tangencies, overlaps, seam crossings and singularities need coverage;
   a simple Newton solve from one seed will miss valid branches.
4. Clip intersection curves to both bounded faces and split their UV regions
   into valid patches, retaining holes and periodic chart relationships.
5. Classify material regions and coincident patches against both operands.
   Generalize the existing classifier to NURBS and other stored types. Treat
   Boundary and Uncertain explicitly, including subtraction orientation.
6. Apply Union/Cut/Common selection rules to the shared partition. Section and
   sheet Split/Trim can use the same intersection/partition services with
   different result rules.
7. Rebuild shared edges, face loops, oriented shells, cavity nesting and bodies;
   validate and attach ancestry/attributes before atomically publishing.

Stage native acceptance in this order: plane/cylinder integration; oblique
cylinder/cylinder; sphere/cone combinations; plane/NURBS; analytic/NURBS;
NURBS/NURBS; periodic/singular cases; cavity and long-chain stress cases.
Each stage needs intersection, partition, classification and assembly, not
just a new pair dispatch. Keep unsupported stages honestly reported.

## Phase 5 — Preserve Blender interaction as kernel scope grows

The normal Blender Object continues to own the datablock. Outliner object names,
collections, parenting and hide/select states can use that same object layer.
This kernel change does not require a FreeCAD-style document tree. Internal
body and shell IDs must not be confused with Blender object IDs. If separate
Outliner objects for result bodies are desired, add an explicit Separate Bodies
operation; a kernel body need not automatically create an Outliner row.

Object Mode move/rotate/scale should stay in Blender's object transform path.
Whole-body Edit Mode transforms should retain the cached affine preview path.
Add affine transforms for NURBS poles and keep weights/knots consistent. Shared
datablock instances, Apply Transform, negative scales and evaluated geometry
need integration checks through existing Blender ownership rules.

Define three distinct component behaviors using Blender's familiar interaction:
- Source vertex/edge/face selection maps through topology IDs and ancestry.
- NURBS control-point edits select actual poles, with G/R/S and optional weights.
- Direct face edits rebuild/reintersect affected neighbors and retrim them.

Specify the direct-edit rule per operation: translating a face, extending an
extrusion cap, extruding a surface region, and offsetting a curved surface are
different constructions. A general NURBS normal offset need not be another
finite NURBS patch; it may need an offset support or a controlled approximation.
Unsupported edits must preserve the valid source. An explicit conversion to
mesh can offer unrestricted mesh deformation when desired.

Keep modal previews responsive using immutable source snapshots, cached
tessellation, dirty-face updates and shared-edge caches. Validate the final
transaction on confirmation. Add dependency-graph tags/notifiers through the
host and preserve undo, cancel, active element and selection modes. Generic
mesh modifiers and Geometry Nodes need an explicit evaluated-display/source
policy; mesh output cannot silently overwrite the Solid source.

Material and texture preservation needs ancestry-based transfer: inherit
surviving face assignments, carry texture UVs through splits, and define mapping
for new cut faces. NURBS UVs alone do not preserve an existing unwrap.

Acceptance for each new Boolean family: Boolean, select the result, G/R/S,
edit a supported face/control point, extrude/bevel where supported, undo/redo,
cancel a drag, duplicate/link, save/reopen, and verify appearance and picking.
Measure both source operation time and actual viewport draw cadence.

## Recommended implementation order and practical limits

Phase 0 first; then the representation, trims, persistence and display work in
Phases 1–2. Establish the native result/history contract in Phase 3. Keep the
build and UI free of an OCCT backend or dependency. Expand native solving in
Phase 4 with editing acceptance from Phase 5
at every milestone. Do not postpone editing until the entire solver is written.

Adding stored NURBS and trims is a substantial kernel expansion. A reliable
general native Boolean solver is a sustained geometry project, not a small
operator rewrite. The code review does not justify a calendar estimate or a
claim of FreeCAD/OCCT parity. Use passed end-to-end milestones as the measure.

This plan preserves the Blender object/Outliner workflow. Achieving equally
natural component editing requires dedicated kernel operations and editor
integration; it does not follow automatically from the B-rep format.
